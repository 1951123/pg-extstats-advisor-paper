\section{Related Work}

The selection problem, hypothetical objects, and offline tuning workflow are
established.  The relevant distinction here is the boundary at which
PostgreSQL extended-statistics state becomes hypothetical while PostgreSQL
remains the semantic authority.

\subsection{Automated statistics management}

MNSA selects statistics using workload, optimizer, and data information while
accounting for maintenance~\cite{chaudhuri2001statistics}; StatAdvisor and
DB2 provide interacting statistical views and column groups
~\cite{elhelw2009statadvisor,db2statviews}.  These establish workload-driven
selection, maintenance concerns, multivariate objects, and contextual utility.
Our RQ3 experiments characterize that behavior only in the supported
PostgreSQL MCV/FD space and introduce no new selection objective.

\subsection{What-if physical design and hypothetical objects}

AutoAdmin's What-If Index Analysis Utility and SQL Server's Database Engine
Tuning Advisor evaluate hypothetical physical configurations without
materializing each proposed structure~\cite{chaudhuri1998whatif,microsoftdta}.
HypoPG provides the closest PostgreSQL pattern: planner-visible,
backend-local hypothetical indexes with session activation and reset
~\cite{hypopg}.  What-if analysis and hypothetical objects are therefore
prior art, not firstness claims here.

The narrower distinction is the state consumed by the native estimator.  In
the validated PG16.14 fragment, the advisor derives native MCV/FD payloads,
retains acquisition identity, represents \texttt{ABSENT\_NATIVE}, and exposes
an ordered active subset to PostgreSQL's extended-statistics path.  PostgreSQL
performs applicability, consumption, deserialization, composition, and CE;
HypoPG provides the analogous backend-local precedent for indexes, not native
MCV/FD payload state.  This is descriptive, not a priority claim or an
assertion that HypoPG cannot be extended.

\subsection{Pending, imported, restored, and statistical-view state}

Oracle supports pending statistics and export/import of collected optimizer
statistics~\cite{oraclependingstats,oracleimportstats}; DB2 establishes
statistics-bearing views, optimizer matching, and workload recommendation
~\cite{db2statviews}.  Testing, transporting, or delaying publication of
precomputed statistics is therefore not claimed as novel.

\begin{sloppypar}
PostgreSQL now documents
\texttt{pg\_restore\_}\allowbreak\texttt{extended\_stats()}, and
and commit material describes restoring values without an immediate
\texttt{ANALYZE}~\cite{postgresql19restore,postgresql19restorecommit}.  This
overlaps with native payload restoration.  We do not claim restoration or
injection novelty, nor that the PG16.14 patch is necessary for future versions.
The distinction is workflow and state lifetime:
\texttt{pg-extstats-advisor} keeps an advisor-side candidate repository and
transiently activates representable ordered subsets for repeated configuration
search, rather than installing one persistent restored state.
\end{sloppypar}

\subsection{Position of \texorpdfstring{\texttt{pg-extstats-advisor}}{pg-extstats-advisor}}

Production/test-server separation, offline advice, and DBA-controlled
deployment are established patterns.  The bounded distinction here is that
the patch stays in the private advisor while production remains stock:
capture supplies a persisted sample and metadata, the advisor reconstructs the
realization and repository, and deployment returns to ordinary DDL.

Our earlier CE-Replay line externalized a bounded CE representation.  The
current system instead retains PostgreSQL as authority and virtualizes the
native state it consumes; CE-Replay is historical context, not the runtime
mechanism or a competing evidence claim.

The inherited prior art therefore includes workload-driven selection,
maintenance-aware recommendation, contextual interactions, what-if design,
hypothetical objects, native optimizer evaluation, restored statistics,
statistical views, and offline tuning.  Within PG16.14's validated
base-relation fragment, our contribution binds advisor-derived native MCV/FD
states (including \texttt{ABSENT\_NATIVE}) to candidate objects, exposes an
ordered active subset to PostgreSQL, and leaves CE semantics native.  The
claim is bounded to the fixed target, arity-two candidates, representable
subsets, and documented predicates; it is not firstness, uniqueness, generic
PostgreSQL support, or a new selection algorithm.
