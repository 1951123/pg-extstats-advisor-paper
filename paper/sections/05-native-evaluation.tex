\section{Native-Semantic What-If Evaluation}
\label{sec:native-eval}

\subsection{Reconstructing a frozen realization}

The evaluator starts from a sealed production-capture bundle, not from a
production catalog snapshot.  The bundle contains the persisted acquisition
sample, workload SQL and identities, exact query truth, portable schema
metadata, and compatibility/environment metadata.  It does not contain
ordinary \texttt{pg\_statistic} rows, extended-statistics payload bytes, or a
payload repository.  This separation keeps capture portable and makes the
advisor-derived statistics realization from the persisted sample an explicit
advisor-side artifact.

The private advisor stages the sample into an isolated relation and applies
the fixed-sample controls required by the PostgreSQL 16.14 patch.  It binds
the sample relation and recorded population size to the session, checks the
relation schema, and reconstructs ordinary and extended statistics from that
same persisted sample.  Candidate shells are created with the requested MCV
or dependency kind and the externally supplied target.  The acquisition path
then performs one relation-grouped \texttt{ANALYZE}; native send functions
serialize \texttt{stxdmcv} or \texttt{stxddependencies} into a repository
entry, or record \texttt{ABSENT\_NATIVE} when PostgreSQL returns a legitimate
null field.

The cache is keyed by the bundle/sample identity, candidate catalog, schema,
PostgreSQL build and patch provenance, and global target.  A cache miss builds
and atomically publishes a validated repository.  A cache hit validates the
manifest and semantic digest, recreates the catalog shells needed for backend
identity, performs the required pre-search shell realization, and reuses the
same repository bytes.  These operations may involve \texttt{ANALYZE}, but
they are acquisition or reconstruction work before the design loop.  Neither
path treats a cache directory or a PostgreSQL OID as semantic identity.

\subsection{Evaluating a design}

For a frozen realization $R$, let $Y$ denote a design represented by an
ordered subset of the candidate catalog.  The evaluator pipeline is:

\begin{center}
\texttt{design $Y$}
\;$\rightarrow$\;
\texttt{register/activate $Y$}
\;$\rightarrow$\;
\texttt{EXPLAIN (FORMAT JSON)}
\;$\rightarrow$\;
\texttt{target Plan Rows}
\;$\rightarrow$\;
\texttt{q-error contribution}.
\end{center}

Registration occurs once when the native evaluator is constructed.  For a
full design evaluation, the adapter activates the ordered shell-OID subset,
executes each workload query with native \texttt{EXPLAIN (FORMAT JSON)}, and
walks the returned plan to locate exactly one node for the target relation.
The numeric \texttt{Plan Rows} value at that node is the estimate used by the
objective; the evaluator does not freeze or reuse a \texttt{PlannerInfo},
\texttt{RelOptInfo}, or final plan.

Let $\widehat{N}_q(Y,R)$ be that extracted target-relation estimate and let
$N_q>0$ be the exact truth bound to query $q$ in the workload bundle.  The
supported positive-truth q-error contribution is
\[
 qerr(q,Y,R)=\max\left(\frac{\max(\widehat{N}_q(Y,R),1)}{N_q},
                         \frac{N_q}{\max(\widehat{N}_q(Y,R),1)}\right).
\]
The current workload objective is the deterministic sum of these contributions
in query-ID order.  Exact truth is therefore an input to evaluation, not a
second estimate obtained from the advisor database.

\subsection{No search-time materialization}

The architectural distinction can be stated with two pipelines:

\begin{description}
\item[Physical per design.] Install a design, run \texttt{ANALYZE}, and call
the native planner.  Repeating this sequence makes each candidate design a
new physical statistics realization.
\item[Current evaluator.] Acquire or reconstruct one frozen candidate
repository before search, activate a design in the backend-local overlay, and
call the native planner.  Search changes optimizer-visible statistics state
without regenerating the candidate payload realization for every evaluated
design.
\end{description}

The current claim is consequently about where work occurs and which state is
reused.  Acquisition and cache reconstruction can run \texttt{ANALYZE} before
search; the search loop has no per-design
\texttt{CREATE}/\texttt{DROP}/\texttt{ANALYZE}.  The reported evidence is
operation counts and exact repeated outcomes, not a measured wall-clock
speedup against a physical-per-design baseline.

\subsection{Query-level conservative reuse}

The evaluator's incremental boundary is a candidate move and a conservative
query incidence set.  For the library's ADD/DROP/SWAP development moves (the
release-qualified product path uses ADD only), the incidence index takes the
union of the queries associated with the move endpoints.  The evaluator
activates the counterfactual ordered design, replans exactly those affected
queries with native \texttt{EXPLAIN}, and copies the previous immutable query
evaluations for every other query.  In pseudocode:

\[
\begin{aligned}
 \text{move endpoints}
 &\;\rightarrow\; \text{candidate--query incidence}
 \;\rightarrow\; A \\
 &\;\rightarrow\; \text{native replan of }A
 \;+\; \text{reuse of }Q\setminus A.
\end{aligned}
\]

The incidence relation is deliberately conservative: false positives cause
extra replanning, while a false negative would be a correctness failure.  The
reuse is exact when $A$ is a conservative superset of all queries whose
native estimate can change.  Incrementality stops at query granularity.  The
system does not cache or mutate planner-internal state, residual clauses,
winner decisions, or an external semantic dependency oracle; each affected
query is replanned by PostgreSQL.

\subsection{Safe objective lower bounds}

The evaluator exposes an exact lower bound for the deterministic search client
when the affected set is conservative.  Since every positive-truth q-error
contribution is at least one, for affected set $A$ and current objective
$L(Y)$:
\[
 LB(Y,A)=L(Y)-\sum_{q\in A}qerr(q,Y,R)+|A|.
\]
The bound gives affected queries their optimistic minimum contribution of one
and retains unaffected contributions.  Thus $LB(Y,A)\ge L(Y)$ cannot strictly
improve the current state, and $LB(Y,A)>L^\star$ cannot beat the incumbent.
These exact tests are applied before native evaluation.  Under the stated
q-error and conservative-incidence contracts, pruning does not change the
move, trajectory, or termination result; it is a bounded search-client
optimization under the current contract.

\subsection{Correctness boundary}

The correctness statement is conditional and deliberately narrow.  Fix one
persisted realization $R$, the same ordinary-statistics state, the same
candidate payload state (including any \texttt{ABSENT\_NATIVE} entries), the
same effective precedence, and the same design $Y$.  Within the supported
PostgreSQL 16.14 fragment, the hypothetical evaluator should return the same
target-relation estimate vector and q-error objective as physical PostgreSQL
using statistics derived from that same realization.  This is a
same-realization semantic-fidelity claim: the overlay leaves estimator
implementation in PostgreSQL.

Realization robustness is a different question.  A future native
\texttt{ANALYZE} may draw a different sample and consequently produce
different payloads, estimates, or selected designs.  Such variation belongs
to the independent-realization robustness evaluation; it does not refute the
same-realization substrate contract.  Conversely, robustness evidence does
not establish design invariance or equality of payload bytes across fresh
realizations.

semantics.

External emulation can be a useful research interface, but it carries a
semantic-duplication and version-maintenance burden and is bounded by the
fidelity of the replicated rules.  The current substrate chooses a different
boundary: retain the hypothetical state while leaving the supported estimator
semantics in PostgreSQL.
