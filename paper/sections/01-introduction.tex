\section{Introduction}

Cardinality estimates guide cost-based query optimization: they influence the
plans that the optimizer compares and therefore the work selected for a
workload. Ordinary per-column statistics often approximate predicates as
independent even when attributes are correlated. PostgreSQL extended statistics
provide multivariate information, including most-common-value (MCV) and
functional-dependency (FD) statistics, that can improve estimates for such
predicates~\cite{ilyas2004cords,postgresql16docs}. Choosing which extended
statistics to maintain is consequently a physical-design task. This task is
not new: workload-driven statistics management and reduction of unnecessary
statistics were studied in MNSA~\cite{chaudhuri2001statistics}, and systems
such as StatAdvisor recommend statistics-bearing objects for a workload while
accounting for interactions~\cite{elhelw2009statadvisor}. A practical design
still has to balance estimator utility against the recurring cost of collecting
and maintaining the selected objects.

The systems obstacle addressed here is the boundary between a candidate
statistics definition and its realized payload. An extended-statistics object
has a definition, but its MCV or FD payload is data-dependent and normally
produced by PostgreSQL's \texttt{ANALYZE} while coupled to catalog state. A
straightforward physical evaluation therefore couples configuration search to
creating statistics, materializing or collecting their payloads, and invoking
the native planner. A workload search that compares many configurations would
repeat that physical-state step. The issue is not merely the number of
candidates: the state needed to evaluate a configuration is ordinarily the
same state that must be physically collected for that configuration. We make no
runtime claim from this observation; it identifies the evaluation boundary
that the system changes.

The surrounding design space is established: AutoAdmin and SQL Server's
Database Engine Tuning Advisor provide what-if analysis
~\cite{chaudhuri1998whatif,microsoftdta}; HypoPG provides backend-local
hypothetical objects~\cite{hypopg}; StatAdvisor and DB2 provide workload and
statistics-bearing recommendations~\cite{elhelw2009statadvisor,db2statviews};
Oracle and PostgreSQL 19 provide statistics testing, transport, or restoration
~\cite{oraclependingstats,oracleimportstats,postgresql19restore}.  Those
families are not claims of this paper.  We address the narrower PostgreSQL
native what-if substrate for extended-statistics payload states selected and
recombined during configuration search.

The central design choice is to virtualize statistics state, not
cardinality-estimator semantics. There are three conceptual alternatives.
Physical evaluation materializes and analyzes each design before asking the
native planner for its response. External CE emulation instead reproduces a
selected set of estimator rules outside the database, which risks divergence
from version-specific applicability, precedence, consumption, and composition.
The current design retains candidate native payload state, activates a
transient backend-local configuration, and delegates the estimate to
PostgreSQL. An earlier CE-Replay design line externalized a bounded subset of
estimator semantics for research experiments; it is historical context, not
the runtime mechanism of the current advisor.

For a candidate catalog $S$ and one frozen realization $R$, each supported
candidate $s\in S$ has a native payload state $P_s(R)$ or an explicit
\texttt{ABSENT\_NATIVE} state. For a representable design $Y\subseteq S$, the
advisor registers the candidate states, activates an ordered subset, and calls
native PostgreSQL \texttt{EXPLAIN}. The backend-local overlay virtualizes
candidate identity, native payload bytes or absence, active membership, and
effective activation order. PostgreSQL continues to execute applicability,
winner selection, clause consumption, payload deserialization, MCV/FD
composition, and numerical cardinality estimation. The Python advisor does
not emulate those CE rules; it supplies the hypothetical state that the native
planner consumes.

The repository is not by itself the what-if mechanism: registration validates
identity and ownership, \texttt{ABSENT\_NATIVE} preserves native absence, and
activation controls the membership and order consumed by the patched lookup
path.  This interface is specific to the validated fragment, not a generic
virtualization theory or replacement for prior hypothetical-object systems.

The realization is \emph{pg-extstats-advisor}: stock production provides a
read-only capture bundle, while a private patched PostgreSQL reconstructs one
frozen realization, evaluates configurations, and emits ordinary advice.  A
DBA reviews and deploys standard DDL and \texttt{ANALYZE}; the patch remains
confined to the private evaluation environment, so advice can continue after
production becomes unavailable.

Search is deliberately a consumer of the substrate rather than the novelty
center. The release-qualified advisor uses deterministic contextual ADD-only
search under a fixed maintenance constraint, an exact q-error objective,
conservative candidate-to-query incidence reuse, and safe lower-bound pruning
where applicable. The product does not claim ADD/DROP/SWAP search novelty or a
global optimum. Richer moves remain development/library functionality and do
not change the product algorithm described here.

The evaluation asks five bounded questions. First, do native hypothetical and
physical states agree for the same persisted realization? Second, can one
acquired repository support many representable configurations without
per-design search-loop \texttt{ANALYZE}, while query-level reuse preserves move
outcomes? We report operation counts, not a speedup over a physical-per-design
baseline that has not been measured. Third, do native interactions make
singleton utility insufficient for contextual physical design? Fourth, can
stock production capture support offline advice, DBA-controlled deployment,
and lifecycle verification? Fifth, how do fixed and selected designs behave
across independent DMV statistics realizations? Same-realization agreement is a
correctness statement. Independent-realization behavior is a robustness
statement: a future \texttt{ANALYZE} may produce different payloads, estimates,
or selected designs without implying a substrate failure.

This paper makes four contributions:

\begin{enumerate}
\item \textbf{Native extended-statistics what-if substrate.} We provide
backend-local registration and ordered activation of supported PostgreSQL
native MCV/FD payload states, including explicit \texttt{ABSENT\_NATIVE}, for
representable hypothetical configurations.
\item \textbf{Native-semantic design evaluation.} Configuration evaluation
delegates statistics applicability, precedence, consumption, composition, and
cardinality estimation to PostgreSQL while reusing unaffected query
contributions. We claim neither a new CE nor a new search algorithm.
\item \textbf{Production-separated advisor realization.} We connect
read-only capture from stock PostgreSQL to private patched-advisor execution,
offline recommendation, and an ordinary stock-PostgreSQL deployment,
\texttt{ANALYZE}, and verification lifecycle.
\item \textbf{Evaluation.} We provide bounded evidence for same-realization
fidelity, contextual candidate behavior, operation counts and repeatability,
production-separated closure, and bounded DMV independent-realization robustness. This is
evidence, not a separate conceptual novelty claim.
\end{enumerate}

The validated scope is PostgreSQL 16.14, one base relation, a fixed supplied
statistics target, arity-two MCV and FD statistics, and the supported predicate
fragment. Broader mechanisms, joins, automatic target optimization, global
search optimality, universal maintenance costs, and query-latency objectives
remain outside the paper's claims.
