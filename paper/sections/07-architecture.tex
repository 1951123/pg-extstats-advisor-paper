\section{Production-Separated Architecture}

The hypothetical overlay is an evaluation mechanism, not a production
deployment requirement.  The architecture therefore separates stock
PostgreSQL 16.14 production from a private advisor zone containing the
patched backend.  The patch registers and evaluates hypothetical
extended-statistics state only before a recommendation is returned.

\subsection{Trust boundary}

The production zone contains stock PostgreSQL, the workload and truth, and a
read-only capture role; capture does not install the overlay, create
statistics, run \texttt{ANALYZE}, or execute deployment DDL.  The advisor zone
contains the patched instance, frozen realization and payload repository,
native evaluator, and fixed-target search client.  After capture,
\texttt{advise} uses only the transferred bundle and private advisor database,
not production credentials.

This separation is an operational boundary rather than a novelty claim.
Offline and test-server tuning are established patterns.  The architectural
role here is to confine the PostgreSQL-specific what-if mechanism to
evaluation while keeping the deployment target conventional.

\subsection{Capture bundle}

The production-side contract is the sealed
\texttt{production-capture-}\allowbreak\texttt{bundle-v1}.  It records environment and
compatibility metadata, portable relation/schema metadata, the supplied
workload, exact full-data truth, the persisted acquisition sample, snapshot
and sampling provenance, and component and root digests.  The bundle is
integrity-checked before transfer and again before advice.  Its sensitivity
declaration is explicit: sampled row values, SQL, constants, and exact truth
may be sensitive, while the bundle is not anonymized or encrypted.

The bundle deliberately does \emph{not} contain ordinary
\texttt{pg\_statistic} rows, native payload bytes, the advisor repository,
search state, or a recommendation.  Digests and the sealed flag provide
integrity and tamper detection, not confidentiality; encryption, access
control, transport protection, and retention remain external responsibilities.

Capture persists the inputs from which the private advisor reconstructs one
frozen realization.  It does not export frozen payloads or the advisor
realization.  The persisted sample is authoritative for replay of that bundle,
but is not claimed equivalent to a future native PostgreSQL \texttt{ANALYZE}
sample.

\subsection{Offline advice}

The offline path validates the bundle, PostgreSQL version, fixed target,
schema, sample method, and workload scope, then stages the sample privately
and reconstructs ordinary-statistics state.  A repository miss creates shells,
applies the target, and derives native MCV/FD payloads or explicit
\texttt{ABSENT\_NATIVE} states; a cache hit validates the cached repository
before reuse.  Acquisition or shell-realization \texttt{ANALYZE} is
pre-search work, not a per-design search operation.

The native evaluator then uses the frozen realization and backend-local
overlay.  The fixed-$T$ contextual ADD-only search evaluates representable
designs and emits a recommendation artifact.  Production may become
unavailable after capture because advice uses only the sealed bundle and
private PostgreSQL instance.

\subsection{DBA-controlled deployment}

The recommendation records selected IDs and definitions, target, maintenance
cost, objective metadata, problem/realization digests, termination metadata,
deployment SQL, and rollback SQL.  It translates hypothetical state into
ordinary PostgreSQL DDL: \texttt{CREATE STATISTICS},
\texttt{ALTER STATISTICS ... SET STATISTICS T}, and \texttt{ANALYZE}.

Deployment is DBA-controlled.  Read-only preflight checks version, target,
schema, catalog visibility, target overrides, name collisions, and equivalent
objects; it is compatibility evidence, not deployment authorization.  The DBA
reviews and executes the DDL and \texttt{ANALYZE} under normal change control,
then invokes verification.  The advisor does not execute production DDL,
change the global target, schedule or run production \texttt{ANALYZE}, or
perform automatic rollback.

\subsection{Rollback and verification}

Verification distinguishes a definition from its materialized state.  It
checks the expected \texttt{pg\_statistic\_ext} definition and the
corresponding \texttt{pg\_statistic\_ext\_data} row.  A missing row is
reported as incomplete and recommends \texttt{ANALYZE}; the verifier never
runs it.  A data row with a legitimate native NULL MCV or dependency field is
reported as a payload warning, not as missing \texttt{ANALYZE}.

Verification checks deployment state only.  It does not compare payload bytes,
rerun CE fidelity, or prove that a fresh production realization matches the
frozen advisor realization.  A production \texttt{ANALYZE} creates a new
realization; this is operational state, not same-realization replay evidence.

If rollback is required, reviewed \texttt{rollback.sql} removes exactly the
recommendation-owned definitions with \texttt{DROP STATISTICS IF EXISTS};
\texttt{verify-rollback} checks that their deterministic names are absent.
Rollback does not restore the pre-advice realization, is not automatic repair,
and provides no transaction-level atomicity guarantee.

\subsection{Reproducibility and release-qualified path}

The release-qualified research-prototype path is an Ubuntu 24.04 Docker
clean-room: stock PostgreSQL capture and production/validation roles surround
a source-built patched PostgreSQL 16.14 advisor used only for private
acquisition and advice.  Runtime users are non-root, and the clean-room
mounts neither host project source nor host environments or data directories.

The Docker path is packaging and reproducibility evidence, not novelty.  It
claims semantic lifecycle reproducibility, such as matching cold/warm design,
objective, and recommendation digests, not byte-identical images, wheels, or
binaries.  It remains a research prototype; bare-host and VM execution are
not release-qualified.

The workflow fails closed on wrong version or target, incompatible schema or
sample metadata, malformed bundles, incompatible maintenance models, and
missing or invalid candidate identity.  It rejects incompatible state rather
than silently reusing stale calibration or payload artifacts.  The invasive
what-if mechanism therefore remains in the advisor zone, while production uses
conventional definitions collected by stock \texttt{ANALYZE}.

The architecture makes no claim of automatic deployment or rollback,
transactional atomicity, fresh-production payload equality, deployment-time CE
verification, an encryption/security platform, or byte-level Docker
reproducibility.  Production remains stock PostgreSQL 16.14 within scope.
