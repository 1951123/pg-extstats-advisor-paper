\section{Advisor Search and Maintenance Constraint}

Search is a client of the native what-if substrate.  The product obtains a
baseline with
\texttt{evaluate\_design}, evaluates moves with \texttt{evaluate\_move}, and
leaves applicability, payload consumption, and cardinality estimation to
PostgreSQL.  Its deterministic contextual ADD-only construction is a scoped,
reproducible client for exercising the evaluator under a maintenance budget.

\subsection{Search as a substrate consumer}

For current design $Y$, an ADD move for unselected $s$ asks the substrate to
evaluate $Y\cup\{s\}$ in context.  The client enumerates moves, supplies them
to the evaluator, and compares $L(Y;R)$; another client can reuse the same
repository, activation, and evaluator with a different policy.

\subsection{Deterministic contextual ADD search}

The release-qualified workflow sets the \texttt{add\_only} field of
\texttt{SearchConfig} to true.  Its product algorithm is a
deterministic contextual ADD-only best-improvement (greedy) construction.  At
each round it enumerates every candidate not in $Y$, rejects a candidate whose
counterfactual design would violate $C(Y')\le B$, applies exact lower-bound
pruning where available, and natively evaluates the remaining moves.  It
accepts the best strictly improving move and repeats from the resulting
design.  A tie is resolved by the lower maintenance cost and then by the
candidate's deterministic rank key; for ADD moves this key is precedence rank
followed by candidate ID.  Candidate enumeration and activation use the same
fixed precedence discipline, so equal inputs produce the same trajectory.

The contextual marginal change for a candidate is
\[
 \Delta(s\mid Y,R)=L(Y;R)-L(Y\cup\{s\};R),
\]
not a fixed singleton score.  The native estimate for $Y\cup\{s\}$ can depend
on active statistics, precedence, and other selected candidates.  This
construction exercises the native substrate under a scoped maintenance
constraint; the library's ADD/DROP/SWAP mode is development-only, whereas the
release-qualified product path is ADD-only.

\subsection{Maintenance constraint}

The search uses Section~\ref{sec:problem}'s notation: candidate cost $c(s)$,
$C(Y)=\sum_{s\in Y}c(s)$, and feasibility $C(Y')\le B$.  The empirical
mechanism-count model is fixed before search, validated against target $T$, and
target/environment-specific: a reproducible first-order resource constraint,
not a universal maintenance law or causal per-candidate \texttt{ANALYZE}
model.  Cost belongs to the definition, so PRESENT and ABSENT\_NATIVE states
have the same cost; the budget check can reject infeasible moves before native
evaluation.

\subsection{Contextual utility}

Utility is contextual: a weak or harmful singleton can improve a design after
another candidate changes applicability, clause consumption, or MCV/FD
composition, while a positive singleton need not remain the best move.  The
evaluator therefore computes $\Delta(s\mid Y,R)$ for current $Y$, not a fixed
score.  This applies established interaction behavior within the supported
fragment.

The release-qualified \texttt{advise\_fixed\_t} path uses the full product
catalog.  Singleton profiles and candidate-set filters are separately
versioned development/artifact interfaces; negative singleton utility remains
diagnostic rather than a generally safe pruning rule.  Any restricted visible
set is an explicit input describing the evaluated catalog.

\subsection{Termination and nonclaims}

The high-level loop is:
\[
\begin{aligned}
Y&\leftarrow\varnothing;\\
&\textbf{repeat:}\\
&\quad\text{enumerate feasible ADD moves;}\\
&\quad\text{prune only with the exact bound;}\\
&\quad\text{evaluate remaining moves natively;}\\
&\quad\text{choose the deterministic best strict improvement;}\\
&\textbf{until none exists.}
\end{aligned}
\]
The result contains selected design $Y$, objective $L(Y;R)$, cost $C(Y)$,
budget $B$, and deterministic trajectory metadata.  Its
\texttt{add-local-optimum} label means that no feasible single ADD move
strictly improves the objective under the current budget and realization.

The conservative incidence index defines the reuse boundary: PostgreSQL
replans the affected set $A$ under counterfactual activation and the evaluator
reuses $Q\setminus A$.  False positives cost planner work; false negatives
would violate correctness.  Incrementality therefore stops at query
granularity, and the exact lower-bound pruning from Section~5 remains a
secondary search-client optimization.

The product path terminates at an ADD-local optimum under the current budget
and realization.  DROP/SWAP remains a development/library capability.  The
maintenance model is scoped to its fixed target and calibration environment;
singleton utility remains diagnostic, and query reuse stops at planner-query
granularity rather than planner-internal state.
